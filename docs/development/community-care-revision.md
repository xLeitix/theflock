# Community care and public activity — design revision

Status: independently reviewed and accepted for implementation after three corrections; see [review record](community-care-design-review.md). The local implementation now passes independent source review,30 API/runtime tests and6 browser tests; see [execution evidence](community-care-validation.md). Location policy incorporates the user's clarification that reports belong to public places. Authority: the user's requested product changes supersede anonymous activity, approved-helper roles, private contribution notes and two-hour helper leases in the original design. The canonical production design incorporates these decisions. Historical specialist/review snapshots remain evidence of their earlier scope.

## Product contract

There are exactly two roles: `member` and `moderator`. A moderator is also a contributing member. Local demo account choices may include two ordinary people to exercise assignment conflicts, but those are accounts, not additional roles. No approval process, helper grant endpoint or helper lease remains.

Public readers see contributors' public display names and comments in the place activity log. New place comments, feeding comments, care descriptions and care-action comments are public plain text. Forms say so before submission. Facebook IDs, internal account IDs, account contact information and provider photos are never included in public DTOs. Names are not proof of unique identity or qualifications.

A member can select **I'll take care of this**, provide a planned calendar date, and optionally add a public comment. The date is a validated real `YYYY-MM-DD` date, interpreted in Europe/Stockholm, today or later at the final new-operation authorization check. The form defaults to Stockholm today; revalidate after fence waits in case local midnight passed. Store it as a date string, not midnight UTC. It is a commitment date, not a claim that work has happened. An overdue commitment remains assigned and is labelled overdue; passing a date does not reopen, resolve or silently transfer a case. Release makes it open. The assignee or a moderator can release; the reporter, assignee or moderator can resolve; only the reporter or moderator can reopen with a fresh observation comment. Any active member can add a public comment to a visible nonpurged case without becoming its assignee or changing its status. A moderator can intervene in abandoned commitments; no automatic dispatch or notification is implied.

Case creation includes **Already handled — mark resolved** and an optional public resolution comment. Creation, resolved state and activity event commit in one transaction. It must never appear briefly as open or require a second client request. A combined `reported_resolved` event represents this path once in the activity log.

## Location boundary

The user clarified that birds belong to places and places are public. A care report references its shared public place; it has no separate bird coordinates. Remove the participant/private detail endpoint and all location-specific access grants. New descriptions, comments, names and report details are public when the place and case are visible. Images remain deferred in the prototype; future visible-case photos are served through a visibility-checked public API from controlled object storage. Hidden/deleted records remain unavailable.

New-place entry offers **Use my location**, and may request it after the user's explicit Add-place action. Use a single browser `getCurrentPosition` request with a bounded timeout and finite maximum age, never continuous tracking. Show locating, accuracy, denied, unavailable, timed-out and unsupported states. Check returned finite coordinates, pilot bounds and stale form-request generation before applying a response. A late response must not overwrite a manual pin edit, a different/new form, a closed form or an already confirmed location. Any coordinate change (manual edit, map click or applied GPS result) clears publicLocationConfirmed. Confirming the current coordinate invalidates any outstanding GPS request; it cannot silently move the point afterward. Offer retry and manual coordinate/pin entry. Do not auto-save or treat GPS as the correct place name. Show the proposed pin and require explicit public-place confirmation; only the confirmed submitted place coordinate goes to the server. Denial must not block creating a place. Production requires HTTPS; loopback development retains the documented local exception. The browser permission/secure-context contract follows [MDN getCurrentPosition](https://developer.mozilla.org/en-US/docs/Web/API/Geolocation/getCurrentPosition). Provider geocoding and live location tracking remain outside scope.

## DTO and HTTP contract for the prototype

All contribution strings are escaped plain text. Empty comments are allowed where optional, bounded at500 characters for a place and1000 for feeding/action comments; care description is3–2000 characters. Display-name length is bounded at the account boundary. All public DTOs remain `no-store`.

- `Role = 'member' | 'moderator'`; demo `Persona = 'member' | 'member2' | 'moderator'`.
- `Place` adds public `comment`.
- `Feeding` adds `authorDisplayName` and `comment`, retaining date, flockBand and foodTypes. `FeedingInput.note` becomes `comment`; `PlaceInput.note` becomes `comment`, plus required `publicLocationConfirmed: true`.
- `CareCase` removes canViewPrivate/claimExpiresAt and adds public `reporterDisplayName`, `assignedDisplayName: string | null`, `plannedDate: string | null`, `description`, `birdCount`, `overdue` and `canComment`, retaining state/version and applicable action capabilities. Public DTOs do not expose internal reporter/assignee IDs.
- `CareInput` adds `resolveImmediately?: boolean`, `resolutionComment?: string`. Its `description` is public for newly submitted reports. Reject superseded note/reason and care-coordinate input fields. It contains no longitude/latitude; the selected public place supplies location.
- `Activity` is a discriminated union represented by `{id,placeId,kind:'feeding'|'care',date,authorDisplayName,comment,feeding?:{flockBand,foodTypes},care?:{caseId,action,issueTypes,plannedDate?}}`. Exactly the matching nested payload is present. IDs are opaque random UUIDs, not timestamp-bearing ObjectIds.
- `GET /api/v1/places/:id/activity` returns `{activity: Activity[],hasMore:boolean}`. It is the place detail's primary history. `GET /places/:id/feedings` remains a supported feeding-only view with the same public name/comment policy.
- `POST /care-cases/:id/claim` accepts `{plannedDate,comment?}`. `POST /care-cases/:id/{release,resolve,reopen}` accepts `{comment?}`; reopen requires a fresh nonempty observation. `POST /care-cases/:id/comments` accepts `{comment}` (1–1000 characters), returns `{case: CareCase}`, and does not change assignment/state. Reopen requires at least3 characters. The dialog can filter the current place's bounded activity response for its events; no extra comment-history endpoint is required for this milestone.
- New resource mutations and comment creation use Idempotency-Key. Existing-case transitions/comments also carry If-Match and append an event atomically with version increment. Current session, CSRF, strict Origin, actor/reporter/parent fences and version checks remain authoritative. Date validation runs only for a new operation after replay lookup, and again after fence waits.

**Cached-client publication boundary (implementation review C4):** stopping old servers does not close old browser tabs. An old feeding form with no note has the same body shape as a new feeding, but previously promised anonymous attribution. Contribution mutations therefore require `X-Flock-Contract: community-care-v2`; missing or incompatible values return409 `CLIENT_UPDATE_REQUIRED` before any contribution change. The revised frontend sends this version and explains public attribution/comments before submission. Authentication and logout remain available without this marker. This is a compatibility acknowledgement, not a secret or replacement for session/CSRF/authorization. Existing sessions alone never prove that the person saw the new publication policy. Regression validation sends a valid old session/CSRF with the old compatible body but no marker and proves no record is created, then proves the current client can submit.

The combined activity stream merges visible feedings by observed time with visible care events by event time, newest first, with a deterministic opaque-ID/type tie-breaker. It returns at most50 items plus truthful `hasMore` in this prototype; full-production pagination uses authenticated-encrypted cursors that do not reveal exact sort timestamps. Care activity action codes are `create | reported_resolved | claim | release | resolve | reopen | comment`. It shows the actor of each event, not merely the original reporter. Do not synthesize a misleading historical actor or exact event time when migrating incomplete legacy data. Feeding recency is derived only from feeding records; a care action never makes a place recently fed. Hidden/deleted places suppress every child/event, and hidden/withdrawn/deleted cases suppress their activity too. Role-specific capability flags never grant access by themselves.

## Migration and erasure

Use versioned, idempotent migration and durable stable IDs. Convert old approved-helper accounts to ordinary members, remove their elevated capability and invalidate affected sessions through authGeneration. Return pre-revision lease-based claims to open; do not invent a person's future commitment or label a system migration as a human care action. Use a migration marker so reruns never release new dated commitments.

New public strings use explicit storage fields such as `comment` and `publicDescription`. Never reinterpret arbitrary old `note`, `reason` or private `description` fields as public. Only allowlisted known synthetic RECORD IDs may have their existing text and attribution converted explicitly; do not authorize migration of every contribution made through a demo account, because a person may have typed private text while testing it. New writes carry explicit public-attribution/public-text metadata. Other legacy text and attribution remain withheld until the author deliberately republishes them; no republication UI is required in this milestone. Public projections resolve the current display name only for eligible public-attribution records, otherwise `Community member`; deleted accounts use `Deleted member`. New onboarding and local contribution forms explain the public-name policy. Do not cache immutable historical name snapshots that defeat rename/deletion.

Account erasure removes public contribution text/name linkage according to the existing erasure policy; feeding rows are removed and recency recomputed, care comments are removed/redacted while minimal anonymous status audit may remain. New public descriptions/comments remain with visible records until moderation/account deletion or an explicitly adopted retention policy; they no longer expire30 days after resolution. Remove legacy exact bird coordinates. At a single recorded migration cutover time, legacy cases that are purged, purge_pending, or retained with purgeDueAt at/before cutover remain terminal and cannot reopen; never restore erased data or revive access that already expired even if the old cleanup worker had not run. Cases with a still-future legacy deadline may migrate to the new lifecycle; their withheld private text remains withheld. Cutover requires stopping/quiescing every old API writer and legacy purge worker before the migration runs, then applying idempotent guarded/transactional migration and recording its version before the revised API accepts requests. A lifecycle marker alone does not constrain unmodified old code. The revised API refuses an unmigrated database, and new workers reject old lifecycle operations. Do not roll back to an old binary after this schema/data transition; fix forward or use a separately reviewed compatibility release. A pre-cutover backup is recovery evidence, not permission to discard later user writes. Migration and any remaining authorized state writes fence/version the same case. Existing session tombstones, account/parent write fences and post-fence legacy-terminal-state revalidation remain required. There is no helper lease deadline to revalidate in the new model.

## Acceptance and review gates

Before implementation: independent review checks role/state transitions, planned-date/replay order, migration publication boundary, merged-history visibility and geolocation consent/races. Resolve substantive design findings first and record the verdict separately from old reviews.

Implementation validation: public reader sees display names/new comments and both activity types; legacy private text/provider IDs never leak; ordinary members can claim with a date and resolve with comment; another member cannot release/resolve the assignment; competing claims yield one winner; comments do not change state; anonymous writes fail; immediate resolved creation/replay produces one resolved report and one combined event; hidden parents/cases suppress history; care events never alter feeding recency; date validation and final authorization survive waits/retries; migration reruns preserve user data; cutover refuses old writers and retains expired/pending/purged legacy terminal cases. Browser tests at390px/1440px cover combined activity, both ordinary personas, immediate resolution, public comments, success/denial/manual geolocation and late-response protection and confirmation reset after each coordinate change. Retain existing CSRF/session/transaction checks.

Production Facebook, images, export/erasure administration, cloud deployment/TLS/backups and verified emergency contacts remain deferred from the local prototype. This revision does not silently declare those implemented.
